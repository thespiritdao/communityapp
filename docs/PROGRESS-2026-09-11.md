## 1. On-chain agreements — BUILT, NOT ARMED

**Shipped** (`401026a1`): creating and signing an agreement are now real
transactions on Base.

- Creating → `addAgreementCriterion(hatId, keccak256(cid), true)`
- Signing → `signAgreement(hash)`, verifiable by anyone via `hasSignedAgreement`
- Gas sponsored through the smart account
- New service: `src/features/pods/services/OnChainAgreementService.ts` — the
  single source of truth for the hash derivation (`keccak256(toHex(cid))`).
  Create and sign **must** agree or signatures verify against nothing.

**Why it had never worked — CORRECTED 2026-09-15.** The paragraph that stood
here said the deployed module was `EligibilityModule` (`0x8E87…`) and that the
sync code targeted the wrong contract. That came from a stale local `.env`.
**Production's `NEXT_PUBLIC_ELIGIBILITY_MODULE_ADDRESS` is
`0x437e353Ad09cA2fc870bAf19D08AEb08cA81B925`, which *is*
`MultiCriteriaEligibilityModule`.** The sync code targeted the right contract;
what blocks it there is that MultiCriteria's `hatAdmins[hat]` is unclaimed for
every pod hat (and `setHatAdmin` is first-come — audit finding F13), plus the
missing pod proxies. Signing works on production; on-chain *creation* reverts
"Only HAT admin" until an admin is claimed from a controlled wallet. See
`App\APP_AUDIT_2026-09-15.md` F12/F13.

**Verified by simulation against Base**, not assumed:

| Call | Result |
| --- | --- |
| `addAgreementCriterion` on TN Member (wallet is hat admin) | succeeds |
| `addAgreementCriterion` on TN Leader (wallet is not) | reverts `NotAuthorized` (`0xea8e4eb5`) |
| `signAgreement` | succeeds (permissionless) |

**Not yet done in the browser.** No real transaction has been watched end to
end, so gas sponsorship and the tx-hash response parsing are unproven.

### Enforcement is OFF — deliberately

Every hat still points at eligibility module `0x4A63A3F3…`. **Correction
(2026-09-15 audit):** that module is `AgentExclusionEligibilityModule`, not a
permissive stub — it returns *ineligible* for Kairos and *eligible* for humans,
so the constitutional agent exclusion on hats is already enforced on-chain.
Agreement criteria written to `EligibilityModule` (`0x8E87…`) gate nothing until
a hat is re-pointed with `Hats.changeHatEligibility`.

> **Do not re-point a hat at `0x8E87…` directly.** It has no registry check, so
> the swap would silently remove the agent exclusion. Arming agreements needs a
> composite module (registry check AND criteria) — see
> `App\APP_AUDIT_2026-09-15.md`, Phase 2.

Once a composite module exists, staging is safe because `EligibilityModule`
treats a hat with **zero criteria as openly eligible** — re-pointing is a no-op
until the first criterion is added.

> **Danger, read before arming.** TN Member has **77 wearers**. The moment an
> agreement criterion is added to a hat pointed at our module, every wearer who
> has not signed becomes ineligible *immediately*. There is no grace-period
> logic in the deployed contract; adding one means writing and deploying a new
> contract. Decide sequencing before touching this.

### Hat-admin boundary

Admin rights follow the Hats tree — you administer hats *below* the one you
wear. The owner's smart account `0xcdf3cd47…`:

- **is** admin of TN Member (wears TN Leader) → can publish there
- **is not** admin of TN Leader or Exec Pod → those need the Community Pod /
  Top hat wearer

An agreement saved on a role you don't administer still saves to the database
and reports "Saved, but not recorded on-chain".

## 2. Platform-wide findings worth acting on

**No `<Toaster />` was ever mounted.** 59 components call `useToast`; not one
message had ever rendered, and production strips `console.log`. Every failure
in the app was silent. Fixed — but it means *anything* previously written off
as working may have been failing quietly. Worth re-testing broadly.

**0 of 5 pods have a deployed proxy contract.** All on-chain eligibility sync
(token balance, time limits) is therefore unavailable platform-wide. Criteria
are enforced in the app and database only. The UI offers "Sync to Blockchain"
regardless; docs may overstate this.

**`management_hat_id` is stored in two formats** — padded hex for 4 pods,
decimal for 1 (Treegens). Lookups now match either; watch for this elsewhere.

**Bounty notifications linked to routes that never existed** (`/bounty/<id>`,
`/bounty/<id>/submissions`, `/bounty/dispute/<id>`). All 404'd since launch.
Now redirect into `/bounty?bounty=<id>`. **Check other notification types for
the same pattern** — only the bounty paths were fixed.
