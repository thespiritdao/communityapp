# RLS Audit (G2b) — Live Database, 2026-08-08

**Method:** Connected directly to the live Postgres (Supabase pooler) and read
`pg_policies` for every table the client writes to directly. This is deployed
ground truth, not repo SQL. 38 client-written tables examined.

**Headline:** RLS is ON for every table (no naked tables). But several sensitive
tables have **permissive write policies (`WITH CHECK true`)** — meaning any
logged-in user can write them regardless of pod role. The worst is
`pod_role_permissions`, the table that *is* the permission model.

---

## ✅ CRITICAL — FIXED & VERIFIED LIVE (2026-08-08)

Migration `supabase/migrations/20260808000001_fix_pod_role_permissions_rls.sql`
applied to prod. INSERT/UPDATE/DELETE now gate on
`is_pod_leader_current_user(pod_id)` (case-insensitive leader check). Verified
against the live DB in rolled-back transactions: non-leader self-grant →
REJECTED, real leader edit → ACCEPTED. Service-role policy preserved for server
routes. Original finding kept below for the record.

> ⚠️ **Follow-up (latent, pre-existing):** the fix uncovered that `pod_leads`
> stores checksummed addresses while `user_profiles.wallet_address` is
> lowercase. The existing `pods` (UPDATE/DELETE) and `knowledge_items` policies
> use an exact-case `= ANY(pod_leads)` comparison that silently fails for
> leaders — they currently "work" only via the `created_by_address` branch or
> service-role writes. Sweep these to the same case-insensitive helper.

## 🔴 CRITICAL (ORIGINAL FINDING) — `pod_role_permissions` was writable by any authenticated user

Live policies on the table that defines every pod's roles and capabilities:

| cmd | role | expression |
|---|---|---|
| INSERT | authenticated | **`true`** |
| UPDATE | authenticated | **`true`** |
| DELETE | authenticated | **`true`** |
| ALL | authenticated | **`true`** ("Pod leaders can manage permissions" — misnamed; not restricted to leaders) |

**Impact — this is the top of the whole threat model.** Any signed-in wallet
can `INSERT`/`UPDATE` a row in `pod_role_permissions` for ANY pod and grant
itself any capability, including `treasuryManagement` and `bountyManagement`.

Chain this with what we just built: our new on-chain treasury proxy (v2.1) and
BountyManagerV5 both check "does the caller wear a hat the pod **registered**
for this capability." Registration is gated on the leader hat on-chain, so the
contracts themselves are safe. BUT the *app's* server-side checks
(`requirePodPermission`, `useHybridPodPermission`) read this table to decide
access — and a self-granted row would pass them. So this single RLS gap
undercuts the app-layer half of the hybrid model for every capability at once.

This also means the entire G2 API-route effort, while correct, sits on top of a
permission table the user can edit. **This must be fixed before launch.**

**Fix:** replace the four permissive policies with ones that require the caller
to wear the pod's management hat (or be a `pod_leads` member). The correct
pattern already exists on this same DB — e.g. `pods` UPDATE uses
`auth.uid() = ANY(pod_leads)` and `pods` DELETE joins `user_profiles` to the
pod creator. Mirror that. Reads (`SELECT true`) are acceptable (permissions are
not secret); only INSERT/UPDATE/DELETE/ALL need tightening.

## ✅ HIGH — FIXED & VERIFIED LIVE (2026-08-08)

Migration `supabase/migrations/20260808000002_fix_high_severity_rls.sql` applied
to prod. Added helper `is_current_user_wallet(text)` (case-insensitive). New
policies, all live-tested with a REAL non-leader member profile and a real
leader (rolled-back transactions):

| Table | New write rule | Verified |
|---|---|---|
| `pod_members` INSERT/UPDATE | pod leader OR the caller's own wallet | self-join ✓ ACCEPT; add-someone-else ✓ REJECT; leader-add ✓ ACCEPT |
| `pods` INSERT | `created_by_address` = caller | as-self ✓ ACCEPT; as-someone-else ✓ REJECT |
| `hats_module_deployments` INSERT/UPDATE/DELETE | pod leader | leader ✓ ACCEPT; non-leader ✓ REJECT |
| `pod_audit_log` INSERT | `performed_by` = caller | own ✓ (RLS passes; unrelated `action` CHECK constraint governs values); forged ✓ REJECT |
| `forum_templates` write | admin-token holder only (dropped the 3 `auth.uid() IS NOT NULL` overrides; `has_admin_token` ALL policy governs) | non-admin ✓ REJECT |

Testing note: an early test run reported false REJECTs for legit cases because
the synthetic test user had no `user_profiles` row (so `is_current_user_wallet`
correctly returned false). Re-tested with a real member profile — all correct.
Original findings kept below.

## 🔴 HIGH (ORIGINAL FINDINGS) — other permissive write policies

| Table | cmd(s) with `true` / weak check | Risk |
|---|---|---|
| `pod_members` | INSERT `true`, UPDATE `true` ({public}) | Anyone can insert/alter pod membership rows → fake membership, which several UI/permission paths trust |
| `pods` | INSERT `true` ({authenticated}) | Anyone can create pod rows (DELETE/UPDATE are correctly leader-gated — only INSERT is open) |
| `forum_templates` | DELETE/INSERT/UPDATE = `auth.uid() IS NOT NULL` | Any logged-in user manages global forum templates (should be admin/leader) |
| `hats_module_deployments` | all = `auth.uid() IS NOT NULL` | Any logged-in user writes deployment records |
| `pod_audit_log` | INSERT `true` | Audit log is forgeable (INSERT open; UPDATE/DELETE correctly `false`) |

## ✅ GOOD — these already encode authority correctly (use as the fix template)

- `knowledge_items` / `knowledge_categories` — INSERT/UPDATE/DELETE all verify
  the caller is a pod leader via a `pods`+`user_profiles` join. **This is the
  gold-standard pattern** for pod-scoped writes.
- `forum_posts` — writes scoped to `author_address = caller's wallet`.
- `forum_moderator_actions` — INSERT requires a `pod_role_permissions` row with
  `forumModeration = true`. (Note: once #CRITICAL is fixed, this becomes truly
  trustworthy; today it leans on the editable table.)
- `governance_votes` — writes scoped to the caller's own wallet.
- `chat_messages` — INSERT/DELETE scoped to sender/receiver = caller's wallet.
- `events` — writes scoped to creator / `auth.uid() = user_id`.
- `pods` UPDATE/DELETE — leader/creator scoped (only INSERT is open).

## ✅ Latent case-sensitivity bug — FIXED & VERIFIED LIVE (2026-08-09)

Migration `20260808000003_fix_case_sensitive_leader_policies.sql`. A full scan
found **32 policies** doing exact-case wallet comparison; checking column casing
in live data narrowed the ACTUALLY-broken set to the pod-leadership family
(`pod_leads`/`created_by_address` — checksummed on 1 pod, Treegens, vs lowercase
`user_profiles.wallet_address`). Confirmed real-world impact: **before the fix,
Treegens' leader (Jimi, checksummed address) was REJECTED creating a knowledge
item in his own pod.** Rewrote these to the case-insensitive
`is_pod_leader_current_user()` helper:
`pods` (UPDATE/DELETE), `knowledge_items`, `knowledge_categories`,
`pod_modules`, `forum_categories` (writes). Verified live (rolled back +
post-apply): checksummed leader now ACCEPTED, non-leaders blocked (RLS filters
to 0 rows / rejects).

**Deliberately NOT changed (works today, flagged):** `events`,
`work_submissions`, `bounty_*` policies compare `creator_address` to a JWT-claim
address. Live data is 100% lowercase (events 0/146 checksummed), so they
function — but remain case-SENSITIVE and would break if a checksummed value is
ever written. Best long-term fix: normalize wallet addresses to lowercase on
write everywhere. Tracked as a follow-up.

## Remediation plan

1. **CRITICAL first:** rewrite `pod_role_permissions` INSERT/UPDATE/DELETE/ALL
   policies to require pod-leadership (mirror `pods`/`knowledge_items`). Draft +
   test on a copy of one policy, confirm a non-leader write is rejected and a
   leader write still passes, then apply. Migration SQL to be prepared for
   review before running against prod.
2. **HIGH:** tighten `pod_members`, `pods` INSERT, `forum_templates`,
   `hats_module_deployments`, `pod_audit_log` INSERT.
3. **MEDIUM:** review the {public} cache/log tables.
4. Add a standing test: a script (like this audit) that flags any
   `WITH CHECK true` write policy on a sensitive table, run in CI/pre-launch.

All changes are RLS policy SQL — no app or contract changes, reversible, and
verifiable with the same live-DB read used for this audit.
