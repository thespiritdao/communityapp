## 1. How are the treasury distribute calls actually submitted? (and: why didn't I know this first?)

**Answer (now traced in code):** They are signed by the **logged-in user's own
CDP smart account** — NOT a shared backend wallet — with gas sponsored by the
paymaster.

- `TreasuryManagement.tsx` builds the distribution and calls
  `sendUserOperation({ evmSmartAccount: currentUser.evmSmartAccounts[0], ...,
  useCdpPaymaster: true })` (lines 461, 498–503).
- So at the proxy, `msg.sender` = the pod manager's smart account.

**Why this matters for the fix:** it's the best possible answer. It means the
hat-check design **works** — we require `msg.sender` (the manager's smart
account) to wear the pod's management hat. Real managers pass; a random EOA
crafting a raw call fails.

**The one caveat to verify (a data question, not code):** the management hat
must be held by each manager's **smart account**, not their login EOA. On-chain
the Exec management hat currently has **3 wearers**; we need to confirm those
are smart accounts. If the hats sit on EOAs instead, we'd re-mint/transfer them
to the smart accounts before the fix goes live. You + the pod leads can confirm
who holds the hat faster than I can enumerate — that's the support I'd ask for.

**On "shouldn't you have known this before changing anything?" — fair.** For the
*mint routes* I did trace callers first, but I missed the "join without a code"
path, which is on me. For the *TreasuryProxy* I flagged the submission question
as an explicit open item BEFORE writing any contract (correct order), and have
now answered it by reading the code. I can and should service this in the audit
itself — which I've now done. No outside knowledge was needed; I just had to
read further. Going forward I'll trace the full submit/sign path before
presenting options, not after.

## 2. Do I have major concerns with open membership (PoC) minting right now?

**No major concern.** Open PoC minting is consistent with your product: anyone
can self-serve a membership token, including joining without an invite code.
The realistic downsides are minor:

- **Gas:** each mint is paymaster-sponsored, so spam = wasted sponsorship $.
  Bounded by the balance dedupe (a wallet already holding PoC is skipped), so a
  single wallet can't repeatedly drain sponsorship — an attacker would need many
  fresh wallets.
- **Vanity/Sybil membership:** someone could script thousands of wallets each
  holding a PoC. But PoC only grants pod-level participation, not DAO-wide
  voting power (that's Advocate, which is now locked). So the blast radius is
  low.

**If you want belt-and-suspenders later** (not required for launch): add a
simple per-IP or per-time rate limit on `mint-poc`, or require the CDP session
to exist. Neither is urgent given the dedupe + low privilege of PoC.

## 3. Does the onboarding guide reflect our intent? What does INTERNAL_API_SECRET actually do?

**Intent:** Yes — the corrected approach matches your model exactly:
- PoC = open self-serve membership (intended). Left open.
- Advocate = donations only (intended). Now enforced: only a server-side caller
  with the secret can mint it.
- Hat = founding user only (already done). Locked to server-side.

**"Why does it matter that people can mint PoC outside the app (beyond gas)?"**
Honestly — for **PoC, it mostly doesn't.** PoC is low-privilege; open minting is
your design. The audit flagged all three mint routes together because they
*looked* identical (no auth), but once we separate them by privilege, only
Advocate (voting power) and Hat (leadership) actually needed locking. Your
instinct is right: PoC being open is not a real problem.

**What INTERNAL_API_SECRET does, specifically:** It's a shared password between
two pieces of YOUR OWN backend. The flow:
1. A donor makes their first donation.
2. `donations/mint/confirm` (server code) decides they've earned an Advocate NFT.
3. It calls `mint-advocate`, adding the header `x-internal-secret: <the secret>`.
4. `mint-advocate` checks: does this header match `INTERNAL_API_SECRET`? If yes,
   mint. If no (or missing), reject with 401.

Because only your server knows the secret, only your server can trigger an
Advocate mint. A random person hitting the route from a browser has no secret →
rejected. That's the whole mechanism: it turns "anyone can mint voting power"
into "only our donation flow can." **You've set it in Vercel — good; that's the
one required step.** (It must match the value in `.env` for local/preview.)

## 4. TreasuryProxy in plain language: can anyone really drain a treasury, why was it missed last week, and will the fix hold?

**Can anyone drain a treasury right now?** In principle, **yes** — but only via
a hand-crafted blockchain transaction sent directly to the proxy contract,
bypassing your app entirely. Nobody using the app can do it (the app checks
manager permissions first). It requires someone technical deliberately going
around the app. So: real, but not "click a button" easy, and the treasuries
hold small balances today.

**Plain-language cause:** Think of the treasury as a vault with a rule: "only
accept withdrawal orders from the Proxy." The Proxy was built to relay orders —
but it relays an order from *anyone* without checking if that person is a pod
manager. So the vault trusts the Proxy, and the Proxy trusts everyone. Chain
those together and anyone can push a withdrawal through.

**Why was it missed last week when we redid treasuries?** Because last week's
work fixed **different** doors:
- The bounty-manager drain (funds pulled from a caller-supplied address) — fixed.
- The treasury upgrade to require multi-sig proposals for manager-initiated
  moves — fixed.

Those hardened the *bounty path* and the *direct-manager path*. This proxy
"sponsored shortcut" is a **third door** that the multi-sig work didn't cover,
because its security was intentionally delegated to the app layer (the DB
permission check) rather than the contract. It wasn't a fix that regressed — it
was a path the earlier fixes never touched. The earlier audits focused on the
contracts we were actively changing; the proxy wasn't in that change set.

**Will the fix hold / get re-flagged later?** The fix moves the manager check
from the app (off-chain, bypassable) into the proxy contract (on-chain,
un-bypassable): before relaying a withdrawal, the proxy asks Hats "does this
caller wear the pod's management hat?" and refuses if not. After that, a future
audit would see on-chain enforcement and NOT flag it — provided we also verify
the caveat in #1 (managers' smart accounts hold the hat). This is the standard,
durable pattern; it won't need redoing.

### If we redeploy the proxy, what else must be redeployed / re-pointed?

Good news: **only the TreasuryProxy contract itself is redeployed.** Nothing
else needs *redeploying*. But several things must be *re-pointed* to the new
proxy address (this is the "everything is linked" lift you dislike, but it's
re-wiring, not rebuilding):

| Thing | Action | Who / how |
|---|---|---|
| The 3 pod treasuries | Re-point `authorizedProxy` to the new proxy | Each via its `SetProxy` **multi-sig proposal** (managers approve) — the only step needing pod leaders |
| `NEXT_PUBLIC_TREASURY_PROXY` | Update to new address | `.env` + Vercel |
| PodTreasuryFactory registry | If it stores the proxy, update it | One owner call (same wallet that fixed the factory registry before) |
| The app | Redeploy so it uses the new address | Vercel deploy |

**What does NOT need redeploying:** the treasuries themselves (just a config
change on them), the bounty manager, the token contracts, the factories,
governance — none of it. The proxy is a relay; swapping it doesn't force
swapping the things it talks to, because the treasuries already have a built-in
"change my proxy" function (via proposal). This is far lighter than the treasury
migration we did — no funds move, no re-registration of pods.

**Recommended sequence:** confirm the hat-holder caveat (#1) → build + verify new
proxy → deploy → managers approve `SetProxy` on each treasury → update env +
registry → redeploy app → test that a non-manager direct call reverts.

**On #6 (vote polling), your question deserves a direct answer:** Your instinct
is right — 2s exists so a just-submitted vote shows near-instantly, and 5 min is
too slow for that. The note in the code is likely a stale comment, not the
intent. Recommendation: keep fast feedback but scope it tightly — poll every 2s
**only for ~30 seconds right after the user submits a vote** (or until their
vote appears), then fall back to a slow 60s refresh. That gives instant
perceived feedback without every idle tab hammering the RPC forever. Even better
long-term: update the UI optimistically on submit (show the vote immediately)
and reconcile on the next slow refresh — then you don't need fast polling at all.
